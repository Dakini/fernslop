# [garden-delete] UI: delete button and confirm dialog on the garden page
**What:** Add `deleteRoom(roomId)` to `GardenService` (`services/types.ts`) with the HTTP implementation (calls [#150](150-garden-delete-api.md)) and the same behaviour in `mockService.ts`, then a "Delete garden" action in the room header of `routes/r.$roomId.tsx` (next to Share/Follow, not on the index cards) that opens the existing `components/ui/alert-dialog.tsx`: it names the garden, says plants, activity, photos and follower emails go for good and it cannot be undone, with Cancel focused first and a clearly destructive "Delete garden" button. On success go to `/`, drop the room from the `rooms` and `room` queries and show a "Garden deleted" toast. Default decision, unless the user changes it: anyone with the link sees and can use the button.
**Why:** Gives people the delete from #150 without an accident-prone one-click action; it is the only guard because there are no accounts.
**Edge cases:** On mobile the button must wrap with the header without overflow and have a 44px tap target, and the dialog must fit a small screen with the buttons stacked (check with the `design-check` skill; `_docs/design-system.md` still describes the old Django templates, so follow the shadcn/palette look of the existing pages, terracotta for the destructive action). Disable the button while deleting (no double submit); a 404 means someone else already deleted it, so treat it as success; any other error keeps the dialog open with an error toast and the garden unchanged. A visitor with the page open elsewhere (or a stale link or bookmark) must see a friendly "This garden was deleted" with a link to all gardens, not a blank page (the `if (!state) return null` in `RoomPage`) or an error toast loop, and the live subscription must stop retrying. The mock service removes the room, its plants, areas and feed, notifies its subscribers, returns 404 semantics for a second delete like the API, and the index shows the empty state when the last garden goes.

# [audit] Double opt-in for follows and a safer digest email
**What:** `POST /api/rooms/{id}/follows` creates an unconfirmed follow and sends a confirmation link (to the `ConsoleSender`, since there is no real sender, see parked #110); only confirmed follows get digests; a new frontend confirm page calls a confirm endpoint. Repeat follows return 201 both times. The digest puts the unsubscribe link first, uses a one-line subject with no user-controlled line breaks, and indents/quotes user text so it cannot look like the system's own lines. Move the token to a fragment (`/unsubscribe#token=`, also for the confirm link) so it never reaches access logs. Cap follows per room and per email per day. Covers audit 3 (bullets 1, 2 digest part, 3, 4, enumeration) and 10.
**Why:** `audit.md` 3 (High): anyone can subscribe any address and author the whole email, a phishing relay once a sender exists; 10: unsubscribe tokens land in uvicorn/CloudWatch logs.
**Edge cases:** A git stash "wip: follow double opt-in + digest" holds an unreviewed partial attempt (`StoredFollow.confirmed_at`, confirm reusing the unsubscribe token, the digest changes, the fragment) that the engineer may use or discard. New fields go in the JSON column, not SQL columns (#140). Existing follows: treat as confirmed or require re-confirmation (PM decides). Old digest links with `?token=` must keep working on the unsubscribe page (done #111); confirmation links expire; unconfirmed follows are purged; the confirm page must not leak whether an address follows. Signed-sender (SPF/DKIM) setup is moved to parked #110.
